# CHM-01 — Локальный импорт регистраций официального GitHub runner

Дата: 2026-09-16. Статус: проект спецификации, реализация не начата.
Целевой проект: форк `quinck-io/chimera`, не приложение sandbox-admin.
База исследования: upstream v0.1.3, commit `0b3b1fe8f41b746e9886dfa7b775a145b16b157d`.

## 1. Задача и результат

Перенести существующую persistent repo-scoped регистрацию официального Linux runner
в локальное хранилище Chimera, сохранив её identity. Не получать новый registration
token, не вызывать регистрацию/удаление runner в GitHub, не менять пользовательские
репозитории, workflow, variables, labels и secrets.

Успех состоит из двух отдельно проверяемых результатов:

1. Offline-импорт безопасно преобразует и сохраняет локальные данные.
2. После отдельно разрешённого переключения GitHub принимает прежнюю identity,
   выполняет jobs и сохраняет регистрацию после job и перезапуска.

Первый результат не доказывает второй. Реальные credentials в ходе исследования
не читались; пригодность всех существующих регистраций не установлена.

## 2. Основания и ограничения

В upstream CLI есть только `register`, `unregister`, `start`, `status`. `register`
генерирует новый RSA-ключ и обращается к registration API. Для импорта этот путь
использовать нельзя. Chimera уже умеет загружать runner identity, OAuth metadata
и RSA-параметры из трёх JSON-файлов.

Входит:

- Linux/X64, github.com, persistent repo-scoped OAuth-регистрации с рабочим V2 flow;
- импорт одной регистрации за вызов, в том числе в root с другими регистрациями;
- dry-run, валидация, идемпотентность, защита от конфликтов и безопасная запись;
- инструкция контролируемого переключения одной разрешённой регистрации.

Не входит:

- GHES, Windows, ephemeral/JIT-регистрации, legacy-only flow;
- реализация FIPS или auth migration;
- массовое переключение 198 сервисов, изменение provisioning/teardown платформы;
- автоматическая остановка systemd-сервисов, изменение labels или GitHub settings;
- исправления executor и обещание совместимости всех пользовательских workflows.

## 3. Предлагаемый интерфейс

Новые команды форка; в upstream v0.1.3 их нет:

```text
chimera import-official --source <official-runner-dir> --name <local-name> --root <chimera-root> --dry-run
chimera import-official --source <official-runner-dir> --name <local-name> --root <chimera-root>
```

`--name` — локальный ключ каталога и списка runners, а не переименование агента
на GitHub. Сохранённый `agentName` остаётся исходным. Имя должно состоять из
латинских букв, цифр, `-`, `_`, `.`; быть длиной 1–128 символов; значения `.` и `..`
запрещены. Разделители пути, абсолютные пути и выход за root недопустимы.

- Успех: exit 0; безопасное резюме `eligible`, `imported` или `already-imported`.
- Ошибка: ненулевой exit и стабильная категория (`invalid-source`,
  `unsupported-registration`, `identity-conflict`, `target-busy`, `write-failed`).
- Вывод не содержит RSA-параметры, токены, OAuth metadata или исходный JSON.
- Dry-run не выполняет сетевых запросов и не создаёт/изменяет файлы, включая
  отсутствующий `config.toml`. Не использовать loader с неявным сохранением defaults.
- Обычный импорт также полностью offline; он не доказывает online-валидность identity.

## 4. Преобразование и eligibility gate

| Вход официального runner | Выход Chimera | Сохраняемая информация |
|---|---|---|
| `.runner` | `runner.json` | agent ID/name, pool ID, оба server URL, GitHub URL, work folder, V2 flow |
| `.credentials` | `credentials.json` | OAuth scheme, client ID и authorization URL из вложенных metadata |
| `.credentials_rsaparams` | `rsa_params.json` | исходные RSA private parameters в совместимом Base64-представлении |

Преобразование структурное, а не копирование/переименование файлов. JSON-названия
полей сверяются с сериализованным форматом официального runner 2.337.0; нельзя
выводить их регистр из имён C# properties. Fixtures создаются из синтетических
данных, не из production credentials.

До записи обязательно:

1. Проверить наличие и читаемость трёх обычных файлов; не следовать symlink на
   credential-файлах. Разрешить source как канонический каталог; отклонить его
   пересечение с целевым каталогом записи.
2. Проверить JSON, обязательные поля, положительные идентификаторы, OAuth scheme,
   repo URL на github.com и необходимые HTTPS V2/OAuth endpoints. Не заменять
   сохранённый endpoint универсальным адресом и не синтезировать отсутствующие поля.
3. Декодировать RSA-параметры и проверить математическую согласованность ключа.
   Не генерировать новый ключ и не изменять public key.
4. Явно отклонить FIPS-required, активную/неоднозначную auth migration,
   ephemeral/JIT и legacy-only регистрации. Неизвестный значимый auth-параметр —
   отказ с безопасной диагностикой, а не молчаливое игнорирование. Дополнительные
   не влияющие на auth поля допускаются по документированному списку.
5. Проверить конфликты локального имени и identity. Ключ identity — GitHub scope,
   pool ID и agent ID; совпадение одного agent ID в разных scopes не конфликт.
6. Сохранить исходные значения без изменения серверной регистрации. Labels
   сохраняются серверно: importer не пытается переустановить их по defaults.

Окончательный список поддержанных auth metadata фиксируется в тестах и документации
форка до приёмки; найденный новый вариант не расширяет scope автоматически.

## 5. Безопасная запись и повторный запуск

Для изменяющего вызова daemon с целевым root должен быть остановлен. Нужна
эксклюзивная локальная блокировка root, совместная для daemon start и операций
изменения конфигурации. Проверка только PID-файла не заменяет блокировку.

Это защищает локальное хранилище Chimera, но не определяет наличие официального
runner на другом хосте. Importer не подключается к GitHub для такого определения.
Запрет двух активных клиентов одной identity обеспечивается процедурой переключения.

- Новые каталоги с credentials: `0700`; JSON с credentials и private key: `0600`.
  Режим задаётся при создании, до записи содержимого, независимо от umask.
- Не следовать symlink в целевом credential-поддереве. Проверять права существующего
  root; при небезопасном доступе отказать, а не менять чужие права молча.
- Сначала подготовить полный набор во временном приватном каталоге на той же FS,
  проверить чтение штатным loader, затем опубликовать каталог без перезаписывания.
- Список `runners` в `config.toml` обновить последним, через атомарную замену файла
  с сохранением остальных настроек. Сбой не должен оставлять конфигурацию,
  ссылающуюся на неполный комплект credentials.
- При сбое между публикацией каталога и обновлением config повторный импорт
  проверяет полный совпадающий комплект и завершает добавление в список.
- Повтор того же импорта — успешный no-op. То же имя с другими данными или та же
  identity под другим именем — конфликт. Флага `--force` нет.
- Уже существующие каталоги и исходные файлы не удаляются и не перезаписываются.
  Убирать можно только временные файлы, созданные текущим незавершённым импортом.

## 6. Переключение и возврат

Только после отдельного разрешения оунера, сначала на одной контролируемой
регистрации без production secrets. Импорт не является разрешением на этот этап.

1. Дождаться отсутствия активного job; штатно остановить официальный runner.
2. Выполнить offline dry-run и импорт; не выполнять `config.sh remove`,
   `chimera register` или `chimera unregister`.
3. Запустить Chimera с одной выбранной identity, проверить job и повторный job
   после перезапуска. Проверить сохранение прежней регистрации и labels.
4. Для возврата остановить Chimera и завершить/дождаться завершения её session;
   затем запустить прежний официальный runner на нетронутых исходных файлах.
5. При session conflict не запускать оба клиента одновременно и не удалять
   регистрацию для «починки». Остановить эксперимент и исследовать причину.

В upstream persistent registration сочетается с `ephemeral: true` в session.
До canary форк должен передавать корректный persistent-признак для импортируемого
типа и покрывать его тестом. Утверждение об автоматическом удалении регистрации
не доказано; доказательство сохранности — два jobs и restart в canary.

## 7. Приёмочные проверки

| ID | Проверка | Ожидаемый результат |
|---|---|---|
| I-01 | Валидная синтетическая V2-регистрация | все поддержанные identity/OAuth/V2 поля и RSA private parameters совпадают с источником после структурного преобразования; public key совпадает; loader принимает файлы |
| I-02 | Dry-run для нового root | FS не изменена, сеть не использована |
| I-03 | Повтор успешного импорта | нет дубля в config, исходники и credentials не перезаписаны |
| I-04 | Другой ключ/identity под тем же именем; дубль identity | безопасный отказ, существующее состояние неизменно |
| I-05 | Нет поля, битый JSON/Base64/RSA, неподдержанный auth/flow | отказ до публикации, секретов в stdout/stderr нет |
| I-06 | Path traversal, symlink, небезопасный root, параллельный writer | отказ без записи за пределами целевого root |
| I-07 | Сбой на каждом этапе записи | config не указывает на частичные credentials; retry восстанавливает согласованность |
| I-08 | Проверка прав при umask 000 | credential-каталоги 0700, файлы 0600 с момента создания |
| I-09 | Разрешённый canary: job → restart → job → возврат | прежняя identity/labels сохранены; официальный runner снова принимает job |

I-01… I-08 — обязательная приёмка реализации offline-importer. I-09 — отдельный
post-implementation gate допуска к миграции; отсутствие разрешения на него не
блокирует завершение разработки и review/PR форка, но блокирует заявление об
online-совместимости и rollout.

В I-01 допустимо только структурное переименование/перемещение полей и канонизация
Base64 при сохранении декодированных значений всех RSA-параметров. Нельзя заменять
endpoint, client ID или ключ «эквивалентным» значением. Сравнение выполняется в
тестах на synthetic fixtures, без печати ключевого материала в диагностику.

Unit/integration тесты используют только синтетические ключи. Online canary
проводится оператором локально; ключи и содержимое credential-файлов не передаются
в чат, LLM, CI artifacts или репозиторий. Без I-09 результат обозначается
«offline-импорт реализован; online-перенос не подтверждён».

## 8. Зависимости, оценка и выдача

Оценка: 1–2 человеко-дня на importer и целевые тесты. Общий integration canary
оценивается отдельно; обнаружение несовместимости протокола требует пересмотра.
Первый проверяемый этап всей инициативы — эта задача. Для простого canary без
Docker она не зависит от CHM-02/CHM-03.

Выдача: код команды, synthetic fixtures и тесты, инструкция dry-run/переключения/
возврата, отчёт I-01… I-09 с явным указанием пропущенных проверок.

Соседние задачи: [CHM-02 — Dockerfile actions](2026-09-16-chimera-dockerfile-actions.md),
[CHM-03 — Docker config](2026-09-16-chimera-job-docker-config.md).
Завершение трёх задач не разрешает массовую миграцию: masking, общий host UID,
post-failure semantics и cancellation executor остаются отдельными рисками.
